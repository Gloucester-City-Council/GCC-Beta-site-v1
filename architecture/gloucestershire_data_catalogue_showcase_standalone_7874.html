Gloucestershire data catalogue

Using a knowledge graph to understand the council information estate

A conventional data catalogue lists datasets one row at a time. A knowledge graph adds the connections between them: which organisations use them, which systems process them, who supplies those systems, and what the data is actually about.

The idea in one sentence Keep the catalogue simple, but make important relationships explicit so patterns emerge across organisations, technology and data.

What is being modelled?

Each important thing becomes a node in the graph. Connections between those things become labelled relationships. The graph does not try to model every field in every database. It starts with a small set of reusable building blocks and becomes richer only where that creates useful understanding.

How to read the graph

Council → USES → System
System → SUPPLIED_BY → Supplier
System → PROCESSES → Dataset
Dataset → ABOUT → Concept

Example: Gloucester City Council uses Civica OpenRevenues. Civica supplies that system. The system processes Council Tax, Housing Benefit and NNDR information. Those datasets can then be tagged with broad concepts describing what the information is about.

The basic building blocks

OrganisationA council or other organisation.
ServiceA council function such as Revenues or Waste.
DatasetAn important body or domain of information.
SystemThe application that stores or processes the data.
SupplierThe organisation providing the technology.
ConceptA broad description of what the data means: Person, Property, Money and so on.

What does this reveal that a spreadsheet does not?

The value is not simply displaying the catalogue as a diagram. Once many catalogue records share the same nodes, patterns emerge across the whole estate.

Technology concentration
Which councils depend on the same system or supplier?
Divergence
Where are councils delivering the same function through different technology?
Semantic overlap
Which datasets contain information about the same things, such as people or property?
Impact
If a system changes, which datasets, services and organisations are affected?
Opportunity
Where could common data, integrations or procurement approaches be reused?
Risk
Where does dependence converge on one supplier, system or information source?

Not everything needs to become a graph node

Ordinary catalogue information can remain as properties of the dataset. It only needs to become a separate node when making it traversable adds value.

Start small and let useful questions drive the detail

The model is deliberately capable of growing without requiring a complete enterprise ontology on day one.

1 · Establish the estateLoad organisations, major datasets, systems and suppliers.
2 · Add meaningTag datasets with a small set of concepts such as Person, Property, Business, Money, Case or Location.
3 · Deepen only where usefulAdd dependencies, sharing, contracts, identifiers, data elements or detailed lineage when there is a real question to answer.

The Gloucestershire revenues example above is illustrative. The working picture shown is that Gloucester, Cheltenham, Cotswold, Forest of Dean and Stroud use Civica OpenRevenues, while Tewkesbury uses NEC Revenues & Benefits.
